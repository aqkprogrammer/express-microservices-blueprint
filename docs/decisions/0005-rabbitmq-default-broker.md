# ADR-0005: RabbitMQ as the default message broker

- **Status:** Accepted
- **Date:** 2026-10-16

## Context

Services communicate asynchronously through domain events (order placed, stock reserved, payment authorized, …) and receive scheduled maintenance commands. The messaging layer must route each event to several independent consumers, survive broker and consumer restarts without losing messages, retry transient failures with back-off, and isolate poison messages. Throughput needs are modest (business events, not telemetry streams) and nothing requires replaying history.

## Decision

Use **RabbitMQ 4.1** with the following topology, defined once in `packages/contracts/src/topology.ts` and declared by the migrator before services start (`scripts/declare-topology.mjs`; `infrastructure/rabbitmq/definitions.json` is an import-ready copy generated by `npm run topology:generate`):

| Element                | Configuration                                                                                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exchanges              | `domain.events`, `maintenance.commands`, `dead-letters` — all `topic`, durable                                                                                                      |
| Routing keys           | `<domain>.<event>.v<version>`, e.g. `order.created.v1`                                                                                                                              |
| Main queue per service | `<service>.events`, **quorum** queue, `x-delivery-limit: 10`, dead-letter exchange `dead-letters`                                                                                   |
| Retry tiers            | `<queue>.retry.1..3`, classic queues with `x-message-ttl` 1 s / 5 s / 15 s (notification-service 2 s / 10 s / 30 s), dead-lettering back to the main queue via the default exchange |
| Dead-letter archive    | `worker.dead-letters`, bound with `#` to `dead-letters`, `x-delivery-limit: -1` (never drops)                                                                                       |

Publishing and consuming (`packages/messaging`):

- **Publisher confirms** on a dedicated confirm channel; `publish` resolves only after the broker confirms (5 s timeout). Messages are persistent.
- **Manual acknowledgements** with a bounded prefetch (default 10). A message is acked only after its outcome is durably handed off (handled, moved to a retry queue, or dead-lettered).
- **Validation on receipt**: the envelope and the payload are parsed with the contract's Zod schema. Malformed messages (`invalid_message`) and unknown types (`unhandled_event_type`) go to the dead-letter exchange immediately; so do handler errors of type `NonRetryableError`.
- Other handler errors are republished to the next retry tier with `x-retry-attempt` and `x-last-error` headers; after the last tier the message is dead-lettered with reason `retries_exhausted`.
- If republishing itself fails (broker trouble), the message is `nack`ed with requeue; the quorum delivery limit eventually dead-letters it natively.
- amqplib 2 connection recovery with re-declaration of consumers after reconnect.

## Consequences

### Positive

- Per-consumer queues give independent delivery and failure handling; a slow notification-service does not delay inventory.
- Quorum queues are replicated (Raft) and the delivery limit protects against messages that crash a consumer before ack.
- TTL-based retry tiers give delayed retries without plugins; the dead-letter archive gives operators a single place to inspect, replay or discard failures (see [runbook: dead letters](../operations/runbook.md#dead-letters)).
- The management UI makes queues, rates and consumers visible during development.

### Negative and trade-offs

- **No replay of history.** Once acknowledged, a message is gone; a new consumer cannot rebuild state from past events. See [ADR-0006](0006-when-kafka-is-appropriate.md).
- **Ordering is not guaranteed** across retries: a retried message re-enters the queue behind newer ones. Consumers are written to tolerate out-of-order and duplicate delivery ([ADR-0011](0011-idempotency.md)).
- Retry queues are classic (non-replicated) queues; messages waiting in a retry tier are less durable than in the quorum queue. Acceptable because the original is acked only after the retry copy is confirmed by the broker.
- Fixed per-queue TTL tiers mean back-off is coarse (three steps).
- Events with no bound queue (currently `InventoryReleased`, `InventoryCommitted`, `NotificationSent`) are routed nowhere and dropped by the exchange; adding a consumer later only receives new events.
- Locally there is a single RabbitMQ node, so quorum replication provides no redundancy until a three-node cluster is used.

## Alternatives considered

| Option                                       | Why not chosen                                                                                                                                                                 |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Apache Kafka                                 | Strong for replay and high throughput, but heavier to operate and the per-message retry/DLQ semantics must be built on top. See [ADR-0006](0006-when-kafka-is-appropriate.md). |
| Redis Streams                                | Would make Redis a durable system of record, contradicting [ADR-0007](0007-redis-not-system-of-record.md).                                                                     |
| NATS JetStream                               | Viable; smaller operational footprint, but less familiar to most teams and fewer managed offerings.                                                                            |
| Cloud queues (SQS/SNS, Pub/Sub, Service Bus) | Good production choices; not runnable fully offline for local development. The messaging package is the seam to replace.                                                       |
| Delayed-message exchange plugin              | Plugin dependency; TTL retry queues achieve the same with core features.                                                                                                       |

## Operational cost

- A RabbitMQ cluster (three nodes recommended for quorum queues in production) or a managed RabbitMQ service.
- Monitoring of queue depth, unacked messages, connection state and dead letters (alerts in `infrastructure/prometheus/alerts.yml`; RabbitMQ exposes Prometheus metrics on port 15692).
- Topology changes (new queue, binding or argument) must be declared by the migrator; changing an existing queue's arguments requires deleting and recreating the queue, which needs a migration plan for in-flight messages.
